Для реализации многокритериальной оптимизации (Парето-оптимальности) в системе **dgdo**, вам необходимо модифицировать логику в **Matching Engine** (компонент на C++), так как именно он отвечает за принятие решений о назначении водителей.

В текущих системах райдхейлинга обычно минимизируется только ETA (время подачи). Чтобы сделать решение Парето-оптимальным для трех сторон (Платформа, Водитель, Пассажир), нужно реализовать метод **скаляризации (конструирования совместного функционала)**, о котором вы спрашивали ранее.

Вот пошаговый план реализации:

### 1. Формирование «Совместного функционала» (Joint Payoff)

В файлах движка сопоставления (обычно это логика в `matching/` или `optimizer/`) нужно заменить простую минимизацию расстояния на максимизацию взвешенной функции $J$:

$$J = \lambda_1 \cdot (\text{Доход платформы}) - \lambda_2 \cdot (\text{Время ожидания}) + \lambda_3 \cdot (\text{Заработок водителя})$$

* **Доход платформы:** Комиссия за поездку минус операционные издержки.
* **Время ожидания (ETA):** Отрицательный фактор (поэтому минус в формуле).
* **Заработок водителя:** Чистый доход водителя с учетом пробега до пассажира.

### 2. Внедрение весовых коэффициентов ($\lambda$)

В конфигурационные файлы `dgdo` (или через API на FastAPI) нужно добавить параметры весов. Изменяя их, вы будете перемещаться по **границе Парето**:

* Увеличение $\lambda_2$ сделает систему идеальной для пассажиров (быстрая подача).
* Увеличение $\lambda_3$ заставит систему отдавать заказы тем, кто дольше стоит без работы или кому выгоднее маршрут.

### 3. Техническая реализация в коде C++

Внутри Matching Engine процесс обычно выглядит так:

1. **Генерация кандидатов:** Система находит всех водителей в радиусе $N$ км от заказа.
2. **Scoring (Скоринг):** Для каждой пары «Водитель — Заказ» рассчитывается значение $J$.
* *Реализация:* Создайте класс `ParetoScorer`, который принимает параметры поездки и вычисляет итоговый балл по вышеуказанной формуле.


3. **Решение задачи о назначениях:** Используйте алгоритм (например, Венгерский алгоритм или аукционный метод), чтобы найти распределение, максимизирующее суммарный $J$ по всем активным заказам.

### 4. Динамическое управление (Differential Game)

Поскольку ситуация на карте меняется (водители движутся), веса $\lambda$ могут меняться динамически:

* Если в районе **дефицит водителей**, платформа может временно увеличить вес $\lambda_1$ (доход) через Surge Pricing.
* Если **водитель долго на линии** и не получал заказов, система может искусственно поднять вес его «Заработка» ($\lambda_3$) для этой конкретной машины, чтобы удержать его в системе (кооперативный аспект).

### Как начать работу с dgdo для этой задачи:

1. **Найдите файл `score_function**` или аналогичный в С++ части репозитория.
2. **Добавьте переменные** для учета стоимости поездки (для платформы) и расхода топлива (для водителя).
3. **Скомпилируйте движок** с новой логикой весов.
4. **Проведите симуляцию:** Посмотрите, как меняется средний доход водителей и время ожидания при разных значениях $\lambda$.

Этот подход напрямую превращает теоретический «joint payoff functional» из вашей книги в рабочий программный код. В данном случае система управления `dgdo` выступает в роли «центрального диспетчера», который решает кооперативную игру за всех участников.
